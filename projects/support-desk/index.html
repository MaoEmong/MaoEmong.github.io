01 / CONTEXT

어떤 문제에서 시작했나요?

고객지원 자동화는 답변 문장을 생성하는 것만으로 완성되지 않습니다. 환불·계정 해킹·제재처럼 사람이 판단해야 할 문의를 구분해야 하고, 같은 서비스에 입점한 다른 고객사의 문의나 내부 초안이 새어나가지 않아야 합니다. Support Desk는 자동 답변과 상담원 업무를 하나의 흐름으로 연결하되 고객사·역할·공개 정보의 경계를 서버에서 유지하는 것을 목표로 했습니다.

게시판과 챗봇은 처리 특성도 다릅니다. 게시판은 접수 후 작업자가 비동기로 답할 수 있지만, 챗봇은 사용자가 스트림을 기다립니다. 그렇다고 분류가 끝나기 전에 문장을 흘려보내면 나중에 이관이 결정되어도 민감한 내용은 이미 보인 뒤입니다. 두 채널이 같은 분류·검색·정책을 사용하면서 저장·재시도·노출 시점을 각 채널에 맞게 다루도록 구성했습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

근거를 보여 주는 답변

고객사의 도움말을 검색해 참고한 문서를 답변에 붙입니다. 문의 게시판과 챗봇을 함께 제공합니다.

02

상담원에게 넘기는 기준

환불·해킹·제재 문의나 신뢰도가 낮은 답변은 상담원에게 넘깁니다. 승인 모드에서는 상담원이 확인한 답변만 고객에게 보입니다.

03

고객사별 운영 화면

문의 상태·긴급도·감정 분류와 처리 현황을 확인합니다. 고객사별 브랜드와 AI 처리 기준을 설정합니다.

한 번의 사용을 따라가 보면

  1. 01

    1. 고객사 포털에서 문의 시작

    고객은 테넌트별 브랜드 화면에서 게시판 문의를 등록하거나 챗봇에 질문합니다. 같은 코드이지만 FAQ·분류 기준·챗봇 이름·허용 링크는 고객사 설정을 읽어 적용합니다.

  2. 02

    2. 분류하고 근거를 찾기

    문의의 유형·긴급도·감정을 분류하고 해당 테넌트 KB만 검색합니다. 분류와 검색 결과를 종합한 신뢰도, 금지 카테고리와 승인 모드를 확인해 자동 응답 여부를 정합니다. AI에는 환불·제재 해제 같은 업무 실행 권한이 없습니다.

  3. 03

    3. 자동 답변 또는 상담원 이관

    허용된 문의에는 참고 문서를 붙여 답하고 티켓 자동 답변을 최대 한 번으로 제한합니다. 이관되면 고객에게 안내하고 상담원에게 초안을 제공합니다. 챗봇 대화는 문의글로 전환해 같은 지원 흐름을 이어갈 수 있습니다.

  4. 04

    4. 상담원의 검토·승인

    상담원은 분류·긴급도·감정·이관 사유로 큐를 살펴보고 초안을 수정·승인·반려합니다. 동시에 같은 초안을 승인하면 버전 조건으로 한쪽에 409를 반환합니다. 고객은 4초 폴링으로 티켓 처리 상태를 확인합니다.

  5. 05

    5. 운영 정책과 지표 조정

    테넌트 관리자는 KB·임계값·금지 카테고리·승인 모드를 설정합니다. 자동해결률은 생성 티켓 중 AI 답변 뒤 고객이 해결을 확인한 티켓을 집계해 계산하고, 이관률과 카테고리 분포도 메시지 수 대신 티켓 기준으로 보여 줍니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    공통 계약을 공유하는 모노레포

    Next.js의 화면·Route Handlers와 contracts·db·queue·ai 패키지를 pnpm workspace로 나눕니다. Zod 계약을 클라이언트와 서버가 공유하고 PostgreSQL·Drizzle이 문의·대화·작업·AI 결과·초안을 저장합니다. pgvector 이미지를 사용하지만 현재 KB 검색 구현은 한글 bigram BM25입니다.

  2. 02

    접수와 작업 등록을 하나의 트랜잭션으로

    게시판 문의는 고객 메시지 저장과 ai_jobs enqueue를 같은 트랜잭션으로 처리합니다. 별도 워커가 lease로 작업을 가져가며 재시도·멱등 키를 관리합니다. AI 패키지는 DB를 직접 쓰지 않고 결과를 반환하며, 완료·공개 답변·자동 응답 횟수 갱신은 서버가 원자적으로 저장합니다.

  3. 03

    정책 판단 뒤에만 열리는 답변 스트림

    챗봇은 분류 → 테넌트 KB 검색 → 정책 판단을 먼저 수행합니다. 금지 카테고리·낮은 신뢰도·승인 모드는 이관하거나 초안으로 남깁니다. 공개 SSE는 분류·근거·토큰·이관·완료·오류의 허용 필드만 보내고 내부 분석과 신뢰도 상세는 서버 기록에 남깁니다.

  4. 04

    테넌트 가드와 역할별 DTO

    서버가 경로 slug를 테넌트로 해석한 뒤 세션 소속과 일치하는지 검사합니다. 저장소 조회에도 tenantId를 전달하며 고객 응답은 공개 메시지와 허용 필드만 구성합니다. 내부 메모·미승인 초안·AI 분석은 고객 DTO에 없고 플랫폼 관리자는 문의 본문 대신 집계를 봅니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

클라이언트가 고른 tenantId를 신뢰하지 않기

마주한 문제
멀티테넌트 서비스에서는 URL이나 요청 본문을 바꾸어 다른 고객사의 문의에 접근하려는 요청을 막아야 합니다. 화면에서 테넌트를 나누는 것만으로는 API를 보호할 수 없습니다.
선택과 구현
공통 가드가 slug로 테넌트를 해석하고 활성 상태·세션 소속을 대조합니다. 변경 요청은 Origin과 CSRF를 검사하고, 저장소에는 서버가 확정한 tenantId만 전달합니다. 타인·타테넌트 리소스는 조회 시 존재를 숨기는 404 정책을 적용하고 역할 부족의 403과 구분합니다.
남은 비용과 한계
테넌트 간 세션 이동을 허용하지 않고 각 API·저장소에 범위를 명시해야 합니다. 테넌트 세션 불일치는 공통 가드에서 미인증으로 처리되므로 리소스 404 정책과 인증 오류를 같은 것으로 설명하지 않습니다.
tenant-guard — 경로·세션·CSRF 검사 ↗
CASE 02

재시도해도 한 번만 공개되는 답변

마주한 문제
워커가 결과를 저장하기 전 멈추거나 lease 만료 뒤 재실행되면 같은 문의에 답변·초안이 중복될 수 있습니다. 처리 중 상담원이 이미 답했는데 늦은 AI 결과가 공개되는 문제도 있습니다.
선택과 구현
메시지·pipelineVersion을 포함한 멱등 키와 sourceJobId·jobId unique 제약을 사용합니다. 워커는 leaseToken·만료를 확인하고 결과 저장 시 티켓 버전·상태·autoReplyCount를 다시 검사합니다. 자동 답변 기록과 카운트 증가는 같은 트랜잭션으로 확정합니다.
남은 비용과 한계
작업 완료와 고객 노출을 함께 관리하므로 상태·제약·복구 코드가 필요합니다. 처리량 수치보다 중복과 오래된 결과를 차단하는 계약을 우선했으며 운영 부하에서의 검증은 남아 있습니다.
API 계약 — 작업·상태·원자성 ↗
CASE 03

빠른 스트리밍보다 먼저 끝내야 할 정책 판단

마주한 문제
챗봇이 생성 즉시 token을 보내면 금지 문의나 승인 모드임을 뒤늦게 알아도 이미 보낸 문장을 회수할 수 없습니다. 내부 검색 점수·신뢰도와 상담원용 분석도 공개 스트림에 섞일 수 있습니다.
선택과 구현
공통 prepare 단계에서 분류·KB 소속 검증·정책을 먼저 완료합니다. 자동 응답일 때만 안전 버퍼를 거쳐 token을 전송하고, 공개 SSE 변환에서 허용 필드만 내보냅니다. 승인 모드에서는 초안 대신 상담원 확인 안내를 고객에게 보냅니다.
남은 비용과 한계
첫 token 전까지 분류·검색 대기가 생깁니다. 출력 정제·의심 입력 이관·허용 링크 정책은 방어 수단이며 실제 모델의 모든 인젝션이나 부정확한 답변을 막는다는 의미는 아닙니다.
AI pipeline — prepare와 정책별 stream 분기 ↗
05 / ROLE & CONTRIBUTION

본인의 역할과 기여

본인은 서로 다른 고객사가 같은 서비스에서 문의를 처리한다는 요구와 고객·상담원·관리자의 작업 방향을 정했습니다. 개발은 Claude Code·Codex가 역할을 나눈 AI 협업 방식으로 진행했습니다. 소스 전체를 수작업으로 단독 구현한 프로젝트로 소개하지 않고 요구·구조·검수 근거를 연결해 설명합니다.

포트폴리오의 핵심은 AI가 답변하는 장면뿐 아니라 자동 답변을 멈추는 정책, 상담원의 승인, 고객에게 내보낼 정보와 내부 기록의 구분입니다. 공개 README·API 계약·핵심 소스·실행 기록을 대조해 이 경계가 어떻게 구현되어 있는지 설명하고, 과거 통과 결과와 데모 계정 변경 뒤 미실행 범위를 구분했습니다.

현재 소개 범위와 한계

  • AI 호출·평가는 Mock만 사용했습니다. Claude 제공자 코드가 있어도 실제 호출·품질·비용·지연을 확인한 것은 아닙니다.

  • 촬영에 사용한 기존 DB의 분류 설정이 초기 버전이라 티켓 FAQ가 이관된 화면이 포함되어 있습니다. 새 시드 기본값·과거 E2E의 FAQ 경로와 구분해야 합니다.
  • 운영 비밀 관리·백업·부하 검증, 비밀번호 변경·열린 대화 목록, 고객 목록 N+1 개선 등이 남아 있습니다. 테넌트 셀프 가입·요금제는 포함하지 않습니다.

다음에 보완할 것

  • 현재 데모 계정과 새 DB로 E2E·시연 시나리오를 재실행하고 기존 분류 설정을 안전하게 전환할 마이그레이션 정책을 정리합니다.
  • 실제 Claude 호출을 별도 평가셋으로 검증한 뒤 운영 관측·백업·부하 시험을 추가하고 고객 목록 조회와 계정 관리 흐름을 보완합니다.
