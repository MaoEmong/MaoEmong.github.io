01 / CONTEXT

어떤 문제에서 시작했나요?

가상 제조사의 품질팀이 고객 불량 신고를 받아 회수 여부를 검토하고, 결정이 내려지면 고객 대응과 교체 물량 배정까지 이어 가는 과제였습니다. 접수한 신고만으로 바로 판단하기 어려워 출하 배치, 확정 불량 수량, 관련 원료를 함께 확인해야 했습니다.

회수 범위가 넓어지면 교체 물량도 달라집니다. 생산 여력이 제한된 상태에서 품질팀이 다음 조치를 찾고, 부서가 기존 안을 거절하면 후속 배정을 다시 결정할 수 있게 하는 데 초점을 뒀습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

불량 신고와 회수 판단

신고를 출하 기록과 대조하고 확정 불량률과 기준을 보여 줍니다. 사람이 안건을 상정하고 위원회 의결을 입력합니다.

02

조건 변경과 재배정

공통 원료 재검사나 회수 실적을 반영해 새 계획을 만듭니다. 부서가 거절하면 원안과 배정 대안을 비교합니다.

03

초안 확인과 출하 점검

AI가 제공하는 초안을 담당자가 확인합니다. 교체분은 최종 품질 확인을 거쳐 출하 가능 상태가 됩니다.

한 번의 사용을 따라가 보면

  1. 01

    클레임 접수와 출하 대조

    고객, 제품, 배치와 영향 수량을 입력하고 출하 기록과 대조합니다. 출하 정보가 맞지 않으면 확인 요청을 남깁니다.

  2. 02

    안건 검토와 회수 의결

    확정 불량률과 회수 기준을 비교하고 근거와 초안을 확인합니다. 품질팀이 상정하고 위원회 의결 결과를 입력합니다.

  3. 03

    재공급 협의와 배정 확정

    회수 교체분을 우선 배정합니다. 새 점검 결과와 회수 실적을 반영해 계획을 다시 계산하고, 부서 거절 시 배정 대안을 비교합니다.

  4. 04

    출하 전 품질 확인

    배정한 교체분은 품질 확인을 거쳐 출하 가능 상태가 됩니다. 보류하면 다음 계획에서 해당 공급 배치를 제외하고 재계산합니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    품질팀 업무 화면

    HTML, CSS와 JavaScript로 구성했습니다. 내 업무와 회수 안건, 재공급 계획에서 현재 상태와 처리할 작업을 확인합니다.

  2. 02

    Node.js 서버와 업무 규칙

    TypeScript로 출하 대조, 불량률 계산, 상태 변경과 재공급 배정을 처리합니다. 기본 업무와 시연은 기록을 따로 사용합니다.

  3. 03

    AI 초안과 가상 데이터

    OpenAI 연결은 선택 사항입니다. 연결 없이도 템플릿으로 업무를 진행할 수 있습니다. 공개본은 고객과 배치, 주문을 새로 만든 예제로 실행합니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

불량률 계산과 회수 승인을 구분

마주한 문제
불량 수량만 보면 출하량이 다른 배치의 위험을 같은 기준으로 비교하기 어렵습니다.
선택과 구현
확정 불량 수량을 출하량으로 나눠 회수 검토 기준과 비교합니다. 기준을 충족하면 안건이 만들어지고 품질위원회 의결을 기록한 뒤에 회수 작업을 시작합니다.
남은 비용과 한계
출하 기록이 없으면 생산량을 대신 사용했다는 표시를 남깁니다. 10% 기준은 업무 규칙을 보여 주는 예시입니다.
불량률 계산과 상태 변경 코드 ↗
CASE 02

부서 제약을 실제 배정에 반영

마주한 문제
회수 교체분, 기존 주문, 유통 수요가 한정된 생산량을 나눠 써야 합니다. 유통 주문을 먼저 보내면 기존 주문이 늦어질 수 있습니다.
선택과 구현
이전 계획을 보존하고 새 버전을 만듭니다. 부서 거절로 협의가 이어지면 원안과 유통팀 선배정안을 비교하고, 모의 결정권자가 고른 안을 실제 배정에 적용합니다.
남은 비용과 한계
생산 여력은 가상 예제의 주당 고정값입니다. 실제 생산 일정을 만들려면 설비와 교대 조건도 반영해야 합니다.
조건 변경과 부서 거절 시연 ↗
CASE 03

AI 초안에 담당자 확인을 남김

마주한 문제
초안이 그럴듯해 보여도 판단 근거나 수량이 정확한지는 담당자가 확인해야 합니다.
선택과 구현
배치와 출하 등 확인 가능한 근거를 AI에 전달해 안건과 고객 안내 초안을 만듭니다. 담당자가 초안을 승인하거나 수정 또는 거부한 결과를 기록하고, 위원회 의결은 별도로 진행합니다.
남은 비용과 한계
키 없이 실행하면 템플릿을 제공합니다. 공개본 검증에서는 템플릿과 담당자 확인을 시험했습니다.
AI 초안 생성 및 대체 처리 ↗
05 / ROLE & CONTRIBUTION

맡은 역할과 기여

개인 참가자로서 품질 이슈와 공급 복구 과제를 선택하고, 접수부터 재공급까지의 범위와 담당자 판단 지점을 정했습니다. 화면을 품질팀 업무 중심으로 정리하고 다른 부서의 영향을 예제로 확인할 수 있도록 설계를 조정했습니다.

Claude와 업무·화면 설계를 검토하고 Codex로 구현과 1차 검증을 진행했습니다. Claude의 2차 검증에 나온 내용을 반영하고, 배포 후 실제 화면을 직접 확인했습니다. 대회 이후 코드를 별도 공개본으로 옮기고 가상 데이터를 새로 작성했습니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

프로젝트 검증 당시의 실행 기록과 코드에 구성한 테스트 항목을 정리했습니다. 각 항목에 실행 조건과 추가 확인이 필요한 범위를 함께 적었습니다.

공개 코드 자동 검증 14개

정상 처리, 새 조건 반영, 부서 거절 후 배정 변경을 포함한 업무 규칙과 서버 검증 14개가 통과했습니다.

새 가상 예제 데이터로 로컬 서버를 실행한 결과입니다.

브라우저 시연 41단계

별도 시연 A~G 41단계를 실행했습니다. 기본 업무에서 접수부터 품질 확인까지 처리하고, 시연을 초기화한 뒤에도 업무 기록이 유지되는지 확인했습니다.

공개본 검증 기록 기준이며 실제 OpenAI 요청은 이번 공개본 확인 범위에 포함하지 않았습니다.

현재 범위와 남은 과제

  • 업무 기록은 서버 메모리에 유지되며 서버 재시작이나 세션 만료 시 사라집니다.
  • 부서별 응답은 한 사람이 대신 입력하는 예제입니다. 실제 계정 권한이나 고객 통지·출하 시스템 연결은 제공하지 않습니다.

다음에 보완할 것

  • 실제 업무에 연결한다면 사용자별 권한, 업무 데이터 보존, 승인 이후 시스템 연동을 먼저 검토합니다.
