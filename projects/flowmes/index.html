FlowMES 제조실행시스템

작업지시에서 생산·품질·재고·설비 기록까지 하나로

자동차 부품 공장을 예로 작업지시·현장 실적·생산 묶음 추적·품질·재고·설비 현황을 연결한 제조실행시스템입니다. 중복 실적 방지, 원본을 남기는 정정과 계산 결과의 대조를 다뤘습니다.

01 / CONTEXT

어떤 문제에서 시작했나요?

공장에서 ‘몇 개 만들었는가’만 저장하면 어떤 자재를 썼는지, 불량이 난 제품이 어디로 이동했는지, 실적을 정정한 이유가 무엇인지 설명하기 어렵습니다. 자동차 부품 공장을 예로 생산·품질·재고·설비 담당자가 같은 기록을 따라가도록 만드는 것을 목표로 했습니다.

현장에서는 같은 실적을 다시 보내거나 연결이 끊긴 뒤 한꺼번에 제출할 수 있습니다. 품질 보류 중인 자재가 출고되거나, 기준정보를 바꿨다는 이유로 과거 작업의 의미가 달라져서도 안 됩니다. 정상 화면뿐 아니라 재전송·정정·상태 변경이 겹치는 조건을 완료 기준에 포함했습니다.

2026년 11월 계획한 8단계 개발과 최종 검사를 마쳤습니다. 완성 범위는 개발 환경에서 확인한 MES 포트폴리오이며, 실제 설비와 운영 데이터로 검증된 공장 운영 시스템이라고 소개하지 않습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

생산과 현장 작업

기준정보·작업 배정부터 자재 스캔·실적·불량 확정과 연결 복구 후 재전송까지 이어집니다.

02

생산 묶음 추적과 품질

생산 묶음(LOT)의 자재·제품 관계를 추적하고, 검사 불합격 묶음의 사용·이동을 막습니다.

03

재고와 정정 이력

입고·이동·출고·실사를 관리하고, 원본을 남긴 반대 기록과 새 기록으로 정정합니다.

04

설비 현황과 생산 지표

시뮬레이터의 설비 메시지를 받아 상태·무응답·교대별 생산 지표를 구분해 표시합니다.

05

품질 통계·공구·예방보전

품질 관리도와 공구 수명, 정비 계획·기록, 리포트 내보내기와 알림을 제공합니다.

06

조회형 AI

허용된 조회로 업무 질문에 답하며 업무 데이터를 변경하지 않습니다. 기본은 규칙 해석이고 실제 모델 연결은 선택 사항입니다.

한 번의 사용을 따라가 보면

  1. 01

    생산 기준을 정하고 작업을 발행

    품목, 자재 구성표(BOM), 공정 순서와 검사 규격을 등록합니다. 관리자가 작업지시를 발행하면 그 시점의 기준 버전을 작업에 고정하고 설비·작업자를 배정합니다.

  2. 02

    현장에서 자재와 실적을 등록

    작업자는 현장 작업 화면에서 배정된 지시를 고르고 자재 바코드를 스캔합니다. 투입·양품·불량 실적을 확정하며, 연결이 끊긴 동안의 요청은 대기열에 남겨 연결 후 다시 보냅니다.

  3. 03

    품질 검사와 재고 이동을 연결

    수입·공정·출하 검사를 확정하고 불합격 생산 묶음(LOT)은 보류합니다. 보류된 묶음의 투입·출고·이동을 막고, 창고와 위치별 잔량 및 입출고 원장을 함께 확인합니다.

  4. 04

    자재에서 제품까지 이력을 추적

    제품 묶음에서 사용 자재를 거슬러 올라가거나, 자재가 사용된 제품을 찾아갑니다. 실적·검사·재고를 정정할 때도 원본과 사유를 남겨 변경 전후를 따라갈 수 있게 합니다.

  5. 05

    현황을 보고 필요한 정보를 조회

    공장 현황판에서 설비 상태와 교대별 생산 지표를 확인합니다. 통계적 품질 관리(SPC), 공구 수명과 예방보전, 리포트·알림을 제공하며 AI 어시스턴트는 허용된 조회 범위 안에서만 답합니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    업무 화면과 현장 작업 화면

    React·TypeScript로 생산·품질·재고·설비 관리 화면과 현장 작업 화면(POP)을 구성했습니다. 사용자는 맡은 역할에 따라 접근하며, 화면은 서버가 계산한 실적·품질·설비 지표를 표시합니다.

  2. 02

    업무 규칙과 변경 기록을 담당하는 서버

    Java 21·Spring Boot 서버가 권한, 작업 상태, 자재 사용 가능 여부와 정정 규칙을 검사합니다. PostgreSQL에 작업·실적·재고 원장과 변경 이력을 저장하고, 같은 요청을 다시 보내도 한 번 처리한 결과를 돌려줍니다.

  3. 03

    설비 수신과 현황 전달

    설비 시뮬레이터의 상태·센서 메시지를 MQTT로 받습니다. 서버에서 설비 상태와 교대별 지표를 계산하고 WebSocket으로 화면에 변경을 전달합니다. 설비 제어와 실제 공장 장비 연결은 이 포트폴리오의 검증 범위에 포함하지 않았습니다.

  4. 04

    규칙을 먼저 정하고 결과를 따로 확인

    화면과 서버를 만들기 전에 API, 권한, 상태 변화와 표시 문구를 문서로 맞췄습니다. Docker Compose로 분리한 시험 환경에서 화면·서버·저장 기록을 함께 검사하고, 주요 계산은 서버 구현과 별개의 계산 사례로 대조했습니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

재전송해도 실적과 재고는 한 번만 변경

마주한 문제
현장 연결이 끊기거나 응답이 늦으면 작업자는 같은 요청을 다시 보낼 수 있습니다. 화면에서 버튼을 막는 것만으로는 생산량이나 자재가 두 번 반영되는 일을 막을 수 없습니다.
선택과 구현
요청마다 식별값을 두고 서버가 처리 결과를 저장하도록 했습니다. 다시 들어온 요청은 기존 결과를 돌려주며, 재고 변경과 그 결과 기록을 하나의 처리 단위로 묶었습니다. 현장 화면의 오프라인 대기열과 서버의 중복 방지를 함께 사용합니다.
남은 비용과 한계
요청 결과를 보관할 공간과 조회 절차가 더 필요합니다. 실제 현장 네트워크와 물리 단말에서 장시간 끊김·복구가 반복되는 조건은 추가 확인이 필요합니다.

CASE 02

잘못된 기록을 지우지 않고 정정

마주한 문제
입출고 기록을 덮어쓰면 당시 재고가 왜 그 수량이었는지 설명하기 어렵습니다. 품질 보류와 재고 이동이 동시에 발생해도 사용하면 안 되는 자재가 이동하지 않아야 합니다.
선택과 구현
재고 원장은 기존 기록을 남기고 반대 기록과 새 기록을 추가하는 방식으로 정정합니다. 생산 묶음의 보류 여부와 잔량을 서버에서 검사하고, 묶음별 잔량·창고 원장·위치별 잔량이 맞는지 별도 대조 기준을 두었습니다.
남은 비용과 한계
이력이 쌓일수록 정정 관계를 조회하고 설명하는 비용이 늘어납니다. 물리 재고와 시스템 재고가 항상 같다는 보장은 아니므로 실사·조정 절차를 별도로 제공합니다.

CASE 03

설비가 조용하다고 정상 가동으로 채우지 않기

마주한 문제
설비 메시지가 오지 않는 구간을 계속 가동했다고 계산하면 생산 지표가 부풀려집니다. 화면과 서버에서 같은 값을 각각 계산하면 서로 다른 숫자가 표시될 수도 있습니다.
선택과 구현
설비의 무응답 구간과 자료가 부족한 값을 구분하고, 교대별 지표는 서버에서 계산해 화면에 전달했습니다. 설비 무응답·생산 지표·품질 통계를 별도의 계산 사례와 대조해 화면과 저장 결과가 같은 기준을 따르는지 확인했습니다.
남은 비용과 한계
늦게 도착한 상태 변화 때문에 가동 시간이 많거나 적게 잡히는 제한은 남아 있습니다. 한 측정에서 186.096초 과대 집계가 확인됐으며, 이 단계에서 해결했다고 표시하지 않았습니다.
설비 무응답·계산 기준 ↗
CASE 04

AI의 답변과 업무 변경 권한을 분리

마주한 문제
사용자의 자연어 질문을 곧바로 데이터베이스 명령으로 실행하면 허용하지 않은 정보 조회나 업무 변경으로 이어질 수 있습니다. 정해진 답을 확인한 시험과 실제 모델의 이해 능력도 구분해야 합니다.
선택과 구현
질문을 미리 허용한 조회로 해석하고, 조회 결과를 바탕으로 답하도록 구성했습니다. 임의의 데이터베이스 명령이나 업무 데이터 수정은 허용하지 않습니다. 기본 실행은 실제 모델을 끈 규칙 해석이며, 실제 모델 연결 시험은 별도 환경에서 분리했습니다.
남은 비용과 한계
자유로운 질문을 모두 처리하지 못하며 허용할 조회를 추가해야 합니다. 실제 모델 20회 호출은 연결 확인 기록이고, 모든 질문에 대한 해석 품질이 검증됐다는 뜻은 아닙니다.

05 / ROLE & CONTRIBUTION

맡은 역할과 기여

자동차 부품 공장을 가정해 다룰 업무와 단계별 완료 기준을 정했습니다. 자체 제작한 픽셀 오피스에서 부장·팀장·팀원으로 구성한 AI 팀에 작업을 배정하고, 생산·품질·재고·설비를 연결하는 방향과 우선순위를 조율했습니다.

AI가 작성한 코드와 시험 결과를 바탕으로 동작을 확인하고, 답변 누락·전달 지연 등 협업 도구에서 생긴 문제도 구분해 점검했습니다. 구현·시험 작성에는 AI 코딩 도구의 지원을 받았으며, 이 포트폴리오는 모든 코드를 직접 작성했다는 주장이 아닙니다.

최종 결과를 공개할 때 기능, 화면과 검증 근거를 정리하고 알려진 제한을 함께 남겼습니다. 실제 공장 적용 경험이나 실제 설비 운영 성과로 확대하지 않고, 개발 환경에서 확인한 범위를 설명하는 데 초점을 맞췄습니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

프로젝트 검증 당시의 실행 기록과 코드에 구성한 테스트 항목을 정리했습니다. 각 항목에 실행 조건과 추가 확인이 필요한 범위를 함께 적었습니다.

최종 8단계 검사 두 회차 통과

2026-11-05 두 회차 모두 판정 기준 29개 항목을 통과했습니다. 브라우저 검사는 회차마다 797건씩 두 번, 총 네 번 모두 통과했으며 실패·재시도·불안정 통과·제외는 0건입니다.

기존 실행 기록 기준입니다. 분리된 개발 시험 환경과 설비 시뮬레이터를 사용했고, 외부 AI 호출은 0건입니다. 두 번째 회차 뒤 개발 환경 자동 복구는 실패했으나 이후 별도 시작 절차로 복구한 기록이 있습니다.

계산과 재고 기록을 별도로 대조

품질 통계 1,238개 값, 생산 지표 242개 값, 설비 무응답 1,037개 값의 독립 계산에서 불일치가 없었습니다. 저장된 생산 지표 41개 키도 재계산과 일치했고, 재고 대조 기준 C1~C5의 위반은 0건입니다.

정해진 시험 사례와 데이터에서 확인한 결과입니다. 실제 공장 부하·장비·운영 데이터에서의 정확성이나 성능을 보장하는 수치는 아닙니다.

조회형 AI와 실제 모델 시험 구분

최종 검사의 AI 정답 대조 52건은 실제 모델을 끈 상태에서 확인했습니다. 실제 모델 호출 20회는 별도 일회용 환경에서 수행했습니다.

규칙 해석의 정답 대조와 실제 모델의 연결 확인을 구분합니다. 실제 모델이 모든 업무 질문을 정확히 해석하는지는 추가 평가가 필요합니다.

검증 근거 보기 ↗

현재 범위와 남은 과제

  • 실제 공장 도입·인증이나 실제 설비·현장 네트워크 검증을 마친 제품은 아닙니다. 화면은 시연 데이터이며 설비 메시지는 시뮬레이터로 만듭니다.
  • 지연 도착한 설비 상태의 가동 시간 오차가 남아 있으며, 과거 시연 데이터에는 수정 결과를 소급하지 않았습니다.
  • MQTT 접속은 개발용 익명 방식입니다. 암호화 접속과 토픽별 권한, 외부 공개용 HTTPS 구성은 운영 전 보완해야 합니다. 2026-10-31 의존성 검사에서 최고 위험 2건·높은 위험 1건이 남아 있습니다.
  • MES 화면은 Chromium 1440×900에서 확인했습니다. 다른 브라우저와 실제 POP 태블릿 해상도는 미확인입니다. 백업 복구 시험도 서버 준비 상태까지만 확인했으며 복구 후 업무 처리는 추가 검사가 필요합니다.

다음에 보완할 것

  • 늦게 도착하거나 순서가 바뀐 설비 메시지를 재처리해 과거 생산 지표를 보정하는 방식을 검증합니다.
  • 실제 도입을 검토한다면 접속 보안·의존성 위험을 먼저 보완하고, 현장 단말·네트워크와 백업 복구 후 업무 흐름을 확인합니다.
  • 실제 AI 모델은 허용된 질문과 거절해야 할 질문을 분리해 해석 품질을 평가합니다.

프로젝트 화면
