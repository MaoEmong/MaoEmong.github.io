01 / CONTEXT

어떤 문제에서 시작했나요?

이음은 흩어진 음성·텍스트·명함을 사람별 기록으로 모으고, 사용자가 확인한 약속을 달력에 연결하는 모바일 서비스입니다. AI가 제안한 내용과 사용자가 확정한 기록을 구분해야 하며, 입력·검수 화면만큼 원본 파일과 서버 응답을 신뢰할 수 있는지가 중요했습니다.

개발 과정에서는 DB의 기록과 파일 참조가 남아 있는데 서버의 예상 경로에서 일부 원본을 찾지 못하는 문제가 드러났습니다. 파일이 실제로 없는 경우와 일시적으로 읽을 수 없는 경우가 같은 오류로 보이면 앱의 복구 안내도 틀어집니다. 또한 개발 인증과 임시 저장 설정이 배포 환경에 섞이지 않도록, 설정 판단이 실제 서버 기동까지 이어지는지 검증할 필요가 있었습니다.

공개 포트폴리오는 이 판단을 읽고 실행해 볼 수 있도록 다시 구성했습니다. 실제 서비스의 비공개 AI·검색 구현이나 운영 정보를 옮기는 대신, 실패 분류와 Spring 생명주기의 작은 예제를 공개합니다. 예제의 현재 동작과 과거 서비스의 배포 기록을 분리하는 것이 설명의 기본 원칙입니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

사람 중심 기록

기록과 일정을 사람 단위로 모으는 서비스 흐름을 소개합니다.

02

파일 오류의 구분

확정된 파일 부재와 권한·연결·불명확한 저장소 오류를 구분하고, 응답과 부작용을 검사합니다.

03

실행 설정 검사

배포 환경에서 위험한 설정 조합으로 서버가 시작되지 않도록 실제 Spring 실행 문맥을 검사합니다.

한 번의 사용을 따라가 보면

  1. 01

    사람별 기록 입력

    음성·텍스트·명함 등으로 기록을 만들고 사람별로 모읍니다. 입력 본문과 전사문·파일 참조를 보존하는 일은 누락 원본을 복구하는 일과 구분합니다.

  2. 02

    제안과 확정 구분

    약속 후보를 바로 확정 일정으로 취급하지 않고 사용자가 검수하도록 구성했습니다. 공개 협업 사례는 후보의 기본 미선택·명시적 확정과 편집 후 돌아가기 경로의 검증을 설명합니다.

  3. 03

    기록·일정·원본 조회

    사용자별 접근을 거쳐 기록과 파일을 읽습니다. 원본 부재가 확정되면 부재 응답을, 저장소 장애라면 별도 오류를 전달해 앱이 원인을 오해하지 않도록 합니다.

  4. 04

    독립 예제에서 판단 검토

    독자는 외부 DB·클라우드 계정 없이 Maven으로 계약을 실행할 수 있습니다. 실제 Spring 요청 처리와 기동 조건의 정상·실패 대조군을 보고 설계 의도를 검토합니다.

  5. 05

    문서·PDF에서 근거 확인

    기술 사례, AI 협업 요약과 검증 문서를 통해 요구·승인·AI 지원·결과를 연결합니다. 공개 예제 검사와 과거 스테이징 배포 확인의 범위를 따로 읽을 수 있습니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    앱의 검수와 서버의 저장 책임

    Flutter·Riverpod 앱은 입력·검수·비동기 상태와 달력을 담당하고, Spring API는 인증·입력 검사와 사용자별 기록·일정·파일 접근을 담당합니다. 일부 추론·OCR·임베딩은 기기에서 처리하며 음성 전사는 서버와 외부 STT를 거칩니다. 완전 오프라인 구조로 설명하지 않습니다.

  2. 02

    관계형 데이터와 파일의 분리

    JPA·PostgreSQL·Flyway로 데이터와 스키마 이력을 관리하고, 원본은 Supabase private Storage에 둡니다. 파일 저장 인터페이스에서 공급자의 실패 의미를 해석합니다. DB 조회 성공만으로 원본 보존을 판단하지 않으며 객체 저장소가 DB와 파일의 원자적 트랜잭션을 제공하는 것도 아닙니다.

  3. 03

    공개 계약을 재구성한 독립 예제

    Java 21·Spring Boot 3.5 계열 예제는 가짜 DocumentStorage와 테스트용 사용자 문맥을 사용합니다. 실제 서비스의 Boot 4 구성·SDK·JWT·DB를 재현하지 않습니다. MockMvc는 MVC 처리·예외 매핑·직렬화를 통과하고, 별도 ApplicationContext 검사는 설정 바인딩과 가드 초기화를 확인합니다.

  4. 04

    서비스 배포와 분리한 포트폴리오 CI

    공개 GitHub Actions는 Java·Dart 예제, 의도적 결함 검출, 공개 범위와 PDF 구조를 검사합니다. 서비스 자격증명을 사용하거나 실제 서비스에 배포하지 않습니다. Python은 문서 생성·검사 도구이며 서비스 백엔드 런타임은 Java·Spring입니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

확정된 파일 부재만 404로 변환

마주한 문제
일반 I/O 오류를 그대로 전달하면 원본 부재를 설명하지 못하고, 모든 저장소 실패를 404로 바꾸면 권한·연결 장애까지 유실로 오인합니다.
선택과 구현
저장소 어댑터가 부재를 확정한 경우에만 도메인 오류로 바꾸고 HTTP 계층이 공개 오류 계약으로 변환하도록 했습니다. 내부 경로·키·원인 메시지는 숨기며 정상 바이트와 읽기 외 부작용도 검사합니다.
남은 비용과 한계
공급자 오류를 보수적으로 분류하므로 불명확한 실패는 부재로 단정하지 않습니다. 공개 예제의 502·503 세분화와 테스트용 소유권 문맥은 새로 만든 계약이며 원래 서비스의 인증·SDK를 복제하지 않습니다.
파일 부재와 장애의 분류 ↗
CASE 02

설정 함수가 아닌 실제 Spring 기동 검사

마주한 문제
테스트 기본값이 앱 설정에 덮이거나 가드 빈이 지연 초기화되면 위험 조건을 검사하지 않고도 통과할 수 있습니다. 무관한 DB 배선 실패를 기동 가드 성공으로 오판할 가능성도 있었습니다.
선택과 구현
위험 조합의 판정과 실제 컨텍스트 기동을 함께 검사합니다. 실패의 최하위 원인·메시지를 확인하고 정상 개발·배포 설정에서는 컨텍스트 활성 상태와 가드 빈의 존재를 대조합니다.
남은 비용과 한계
공개 예제는 작은 컨텍스트로 생명주기를 확인합니다. DURABLE이라는 선언이나 정상 기동이 실제 저장소의 접근·영속성, 서비스 전체 자동 구성을 보장하지는 않습니다.
실행 설정과 예제 검사 범위 ↗
CASE 03

테스트의 통과와 결함 탐지 능력 구분

마주한 문제
정상 테스트의 통과만 보면 테스트가 의도한 결함을 실제로 잡는지 알기 어렵습니다. 컴파일 오류나 의존성 다운로드 실패를 의도한 실패로 잘못 인정해서도 안 됩니다.
선택과 구현
테스트 전용 구성에서 모든 저장소 실패를 404로 바꾸거나 기동 가드를 빼고 같은 두 계약이 실패하는지 확인합니다. 새 Surefire XML의 테스트 이름·단언 원인을 확인한 뒤 정상 구현에서 같은 계약의 통과를 대조합니다.
남은 비용과 한계
현재 포트폴리오를 위해 만든 결함 모델입니다. 과거 서비스의 수정 전 코드·당시 개발 순서·작성자를 입증하지 않으며, 기본 검사의 조건부 스킵과 별도 시연 결과를 구분합니다.
독립 결함 주입 시연 ↗
05 / ROLE & CONTRIBUTION

본인의 역할과 기여

1인 주도로 요구사항·사용자 시나리오와 수정 승인을 담당하고, AI 코딩 에이전트를 분석·구현·테스트 실행에 활용했습니다. 파일 오류에서는 기록·전사문·참조를 보존하는 수정 범위를, 배포 설정에서는 개발 편의와 배포 차단이 함께 성립하는 조건을 정했습니다. AI가 수행한 코드 작업과 주도자의 요구·승인을 구분합니다.

공개 협업 자료는 개발 대화를 바탕으로 다듬은 의사결정 요약과 사후 기록입니다. 원문 대화나 원본 실행 로그의 재현으로 표시하지 않습니다. 독립 코드·기대 응답·CI를 통해 현재 검토 가능한 근거를 만들었으며, 코드 생성 비율이나 시간 절감률은 측정하지 않았습니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

아래 결과는 연결된 공개 문서의 기록입니다. 이 소개 페이지를 갱신하면서 원본 프로젝트의 검사를 다시 실행한 결과는 아닙니다.

공개 Java·Spring 예제

2026-09-08 기록은 정상 계약 20개 통과·결함 데모 2개 기본 스킵, 별도 결함 2개 탐지 후 정상 구현의 같은 계약 통과입니다.

MockMvc 9개와 Spring 컨텍스트 11개를 다루는 독립 예제입니다. 이번 소개 작성 중 재실행하지 않았습니다.

과거 서비스 회귀·배포

백엔드 210개·앱 834개 통과와 조건부 스킵 17개, CI·스테이징 배포 확인이 정리되어 있습니다.

과거 내부 기록의 재정리입니다. 검사 집합은 중복 가능해 합산하지 않으며 커버리지·AI 정확도·스토어 출시를 뜻하지 않습니다.

파일 보존과 공개 CI

신규 합성 사진 1개를 서버 재배포 후 새 앱 프로세스에서 재조회하고 바이트를 대조한 기록이 있습니다. 공개 CI는 예제·문서·PDF 검사를 정의합니다.

한 파일의 보존 확인이며 기존 누락 원본 복구가 아닙니다. CI 설정을 읽은 것으로 현재 실행 성공을 새로 확인한 것은 아닙니다.

검증 근거 보기 ↗

현재 소개 범위와 한계

  • 비공개 서비스 전체 소스·원본 Git 이력·핵심 AI·검색 구현·운영 자격증명은 공개하지 않습니다.
  • 예제는 가짜 저장소와 테스트용 인증 문맥을 사용합니다. 실제 SDK·JWT·DB·보안 필터 체인의 종합 검증이 아닙니다.
  • 기존 누락 원본은 복구하지 못했으며 AI 약속 추출·검색 정확도와 환각률의 확정 수치는 없습니다.
  • 실기기 캡처가 아닌 합성 화면입니다. iOS 실기기·스토어 서명과 출시·알림·외부 캘린더 연동은 완료 범위 밖입니다.

다음에 보완할 것

  • 파일 수명과 DB 참조가 어긋나는 추가 실패 조건을 정리하고, 실제 공급자 연결 검사와 독립 계약 검사 사이의 차이를 유지합니다.
  • 사용자 시나리오별 추출·검색 평가 기준을 만들고, 정확도와 실패 사례를 측정한 뒤 제품 품질 근거로 공개합니다.
