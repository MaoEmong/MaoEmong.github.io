01 / CONTEXT

어떤 문제에서 시작했나요?

이음은 흩어진 음성·텍스트·명함을 사람별 기록으로 모으고, 사용자가 확인한 약속을 달력에 연결하는 모바일 서비스입니다. AI가 제안한 내용과 사용자가 확정한 기록을 구분해야 하며, 입력·검수 화면만큼 원본 파일과 서버 응답을 신뢰할 수 있는지가 중요했습니다.

개발 과정에서는 DB의 기록과 파일 참조가 남아 있는데 서버의 예상 경로에서 일부 원본을 찾지 못하는 문제가 드러났습니다. 파일이 실제로 없는 경우와 일시적으로 읽을 수 없는 경우가 같은 오류로 보이면 앱의 복구 안내도 틀어집니다. 또한 개발 인증과 임시 저장 설정이 배포 환경에 섞이지 않도록, 설정 판단이 실제 서버 기동까지 이어지는지 검증할 필요가 있었습니다.

파일 오류 분류와 배포 설정 검사를 외부 DB·클라우드 계정 없이 실행할 수 있는 Java·Spring 예제로 정리했습니다. 공개 저장소에서는 두 문제의 정상·실패 조건을 직접 비교할 수 있습니다. 전체 서비스의 AI·검색 구현은 비공개로 유지하고, 서비스 개발 당시의 배포·검증 기록은 별도 문서에 담았습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

사람 중심 기록

음성·텍스트·명함 기록과 확인한 약속을 사람별로 모읍니다.

02

파일 오류의 구분

확정된 파일 부재와 권한·연결·불명확한 저장소 오류를 구분하고 응답과 부작용을 검사합니다.

03

실행 설정 검사

배포 환경에서 위험한 설정 조합으로 서버가 시작되지 않도록 실제 Spring 실행 문맥을 검사합니다.

한 번의 사용을 따라가 보면

  1. 01

    사람별 기록 입력

    음성·텍스트·명함으로 기록을 만들고 사람별로 모읍니다. 파일 조회가 실패해도 입력 본문과 전사문·파일 참조를 보존해 사용자가 남긴 기록을 유지합니다. 기존 누락 원본의 복구는 별도 과제로 남아 있습니다.

  2. 02

    제안과 확정 구분

    약속 후보는 사용자가 검수한 뒤 확정하도록 구성했습니다. 후보의 기본 상태는 미선택으로 두고, 명시적 확정과 편집 후 돌아가기 경로를 검증 항목으로 다뤘습니다.

  3. 03

    기록·일정·원본 조회

    사용자별 접근을 거쳐 기록과 파일을 읽습니다. 원본 부재가 확정되면 부재 응답을, 저장소 장애라면 별도 오류를 전달해 앱이 원인을 오해하지 않도록 합니다.

  4. 04

    독립 예제에서 판단 검토

    독자는 외부 DB·클라우드 계정 없이 Maven으로 계약을 실행할 수 있습니다. 실제 Spring 요청 처리와 기동 조건의 정상·실패 대조군을 보고 설계 의도를 검토합니다.

  5. 05

    문서·PDF에서 근거 확인

    기술 사례, AI 협업 요약과 검증 문서를 통해 요구·승인·AI 지원·결과를 연결합니다. 공개 예제 검사와 과거 스테이징 배포 확인의 범위를 따로 읽을 수 있습니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    앱의 검수와 서버의 저장 책임

    Flutter·Riverpod 앱은 입력·검수·비동기 상태와 달력을 담당하고, Spring API는 인증·입력 검사와 사용자별 기록·일정·파일 접근을 담당합니다. 일부 추론·OCR·임베딩은 기기에서 처리하며 음성 전사는 서버와 외부 STT를 거칩니다. 음성 전사처럼 서버와 외부 서비스가 필요한 작업에는 네트워크 연결이 필요합니다.

  2. 02

    관계형 데이터와 파일의 분리

    JPA·PostgreSQL·Flyway로 데이터와 스키마 이력을 관리하고, 원본은 Supabase private Storage에 둡니다. 파일 저장 인터페이스에서 공급자의 실패 의미를 해석합니다. DB 조회 성공만으로 원본 보존을 판단하지 않으며 객체 저장소가 DB와 파일의 원자적 트랜잭션을 제공하는 것도 아닙니다.

  3. 03

    오류·기동 조건을 재현하는 독립 예제

    Java 21·Spring Boot 3.5 계열 예제는 가짜 DocumentStorage와 테스트용 사용자 문맥을 사용합니다. 실제 서비스의 Boot 4 구성·SDK·JWT·DB를 재현하지 않습니다. MockMvc는 MVC 처리·예외 매핑·직렬화를 통과하고, 별도 ApplicationContext 검사는 설정 바인딩과 가드 초기화를 확인합니다.

  4. 04

    독립 예제와 문서를 검사하는 CI

    공개 GitHub Actions는 Java·Dart 예제, 의도적 결함 검출, 공개 범위와 PDF 구조를 검사합니다. 서비스 자격증명을 사용하거나 실제 서비스에 배포하지 않습니다. Python은 문서 생성·검사 도구이며 서비스 백엔드 런타임은 Java·Spring입니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

확정된 파일 부재만 404로 변환

마주한 문제
일반 I/O 오류를 그대로 전달하면 원본 부재를 설명하지 못하고, 모든 저장소 실패를 404로 바꾸면 권한·연결 장애까지 유실로 오인합니다.
선택과 구현
저장소 어댑터가 부재를 확정한 경우에만 도메인 오류로 바꾸고 HTTP 계층이 공개 오류 계약으로 변환하도록 했습니다. 내부 경로·키·원인 메시지는 숨기며 정상 바이트와 읽기 외 부작용도 검사합니다.
남은 비용과 한계
불명확한 공급자 오류는 장애로 남겨 실제 파일 부재와 구분합니다. 독립 예제에서는 502·503 응답과 테스트용 소유권 문맥을 별도로 구성했으며 실제 서비스의 인증·SDK 연결은 제외했습니다.
파일 부재와 장애의 분류 ↗
CASE 02

설정 함수가 아닌 실제 Spring 기동 검사

마주한 문제
테스트 기본값이 앱 설정에 덮이거나 가드 빈이 지연 초기화되면 위험 조건을 검사하지 않고도 통과할 수 있습니다. 무관한 DB 배선 실패를 기동 가드 성공으로 오판할 가능성도 있었습니다.
선택과 구현
위험 조합의 판정과 실제 컨텍스트 기동을 함께 검사합니다. 실패의 최하위 원인·메시지를 확인하고 정상 개발·배포 설정에서는 컨텍스트 활성 상태와 가드 빈의 존재를 대조합니다.
남은 비용과 한계
예제는 작은 Spring 컨텍스트에서 기동 조건을 검사합니다. DURABLE 설정을 사용하더라도 실제 저장소 접근·파일 영속성과 서비스 전체 자동 구성은 별도 통합 검증이 필요합니다.
실행 설정과 예제 검사 범위 ↗
CASE 03

테스트의 통과와 결함 탐지 능력 구분

마주한 문제
정상 테스트의 통과만 보면 테스트가 의도한 결함을 실제로 잡는지 알기 어렵습니다. 컴파일 오류나 의존성 다운로드 실패를 의도한 실패로 잘못 인정해서도 안 됩니다.
선택과 구현
테스트 전용 구성에서 모든 저장소 실패를 404로 바꾸거나 기동 가드를 빼고 같은 두 계약이 실패하는지 확인합니다. 새 Surefire XML의 테스트 이름·단언 원인을 확인한 뒤 정상 구현에서 같은 계약의 통과를 대조합니다.
남은 비용과 한계
독립 예제에 의도적으로 넣은 결함으로 테스트의 탐지 능력을 확인했습니다. 과거 서비스의 수정 전 코드를 재현한 모델은 아니며, 결함 시연은 기본 검사에서 제외하고 별도 명령으로 실행하도록 구성했습니다.
독립 결함 주입 시연 ↗
05 / ROLE & CONTRIBUTION

맡은 역할과 기여

서비스를 1인 주도로 진행하며 요구사항과 사용자 시나리오를 정하고 수정안을 검토·승인했습니다. AI 코딩 에이전트는 분석·구현·테스트 실행에 활용했습니다. 파일 오류를 처리할 때는 기록·전사문·파일 참조를 보존하도록 범위를 정했고, 배포 설정에서는 개발 편의를 유지하면서 위험한 조합의 서버 기동을 막도록 조건을 구체화했습니다.

파일 오류 분류와 Spring 기동 조건을 외부 계정 없이 실행할 수 있는 독립 예제로 정리했습니다. 정상 응답과 실패 응답을 대조하는 테스트, 결함을 주입해 검사 효력을 확인하는 예제, CI 설정과 검증 문서를 함께 구성했습니다. 개발 대화에서 다룬 요구·판단·AI 지원 작업은 의사결정 요약으로 남겼습니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

프로젝트 검증 당시의 실행 기록과 코드에 구성한 테스트 항목을 정리했습니다. 각 항목에 실행 조건과 추가 확인이 필요한 범위를 함께 적었습니다.

공개 Java·Spring 예제

2026-09-08 정상 계약 20개가 통과했습니다. 기본 실행에서 제외한 결함 데모 2개는 별도 실행으로 결함을 탐지하고, 정상 구현이 같은 계약을 통과하는지 대조했습니다.

MockMvc 9개와 Spring 컨텍스트 11개를 다루는 독립 예제입니다. 실제 서비스 전체를 실행하는 통합 검사는 별도 범위입니다.

현재 범위와 남은 과제

  • 전체 서비스 소스·원본 Git 이력·핵심 AI·검색 구현과 운영 자격증명은 비공개입니다.
  • 공개 예제는 가짜 저장소와 테스트용 인증 문맥을 사용합니다. 실제 SDK·JWT·DB·보안 필터 체인을 연결한 검증은 별도 범위입니다.
  • 기존 누락 원본 복구는 미해결입니다. AI 약속 추출·검색 정확도와 환각률의 정량 평가도 남아 있습니다.
  • 소개 화면은 Flutter 위젯을 합성 데이터로 렌더링했습니다. iOS 실기기·스토어 서명과 출시·알림·외부 캘린더 연동은 후속 과제입니다.

다음에 보완할 것

  • 파일 수명과 DB 참조가 어긋나는 추가 실패 조건을 정리하고, 실제 공급자 연결 검사와 독립 계약 검사 사이의 차이를 유지합니다.
  • 사용자 시나리오별 추출·검색 평가 기준을 만들고, 정확도와 실패 사례를 측정한 뒤 제품 품질 근거로 공개합니다.

08 / SOURCE MATERIAL
