01 / CONTEXT

어떤 문제에서 시작했나요?

인사 업무는 사원 한 명의 정보를 수정하는 화면만으로 끝나지 않습니다. 부서를 옮기면 현재 소속과 발령 이력이 함께 바뀌어야 하고, 휴가를 신청하면 승인 전에도 사용 가능한 잔액이 줄어야 합니다. 급여가 확정된 뒤에는 사원의 이름이나 소속이 바뀌더라도 당시 명세를 같은 내용으로 조회할 수 있어야 합니다. EMS는 이런 업무 간 연결과 변경 순서를 백엔드에서 일관되게 유지하는 것을 중심 과제로 삼았습니다.

또 다른 과제는 민감한 업무에 AI를 어디까지 허용할지 정하는 것이었습니다. 검색 제안이 기존 조건을 조용히 덮거나 생성된 평가 요약이 확정 점수보다 더 권위 있게 보이면 사용자가 결과를 오해할 수 있습니다. 따라서 AI의 역할을 검색 조건 제안, 확정 평가의 읽기 전용 요약, 합성 규정 Q&A로 좁히고 권한·전송 범위·명시적 적용을 제품 흐름 안에 포함했습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

조직과 사원 관리

로그인·권한, 사원·부서·직급, 발령·퇴사 이력과 조직도를 관리합니다.

02

근태·급여·평가

근태 정정, 휴가 예약·결재, 월별 데모 급여 생성·확정, 자기·관리자 평가를 연결합니다.

03

AI의 명시적 사용

검색 필터 제안, 확정 평가의 읽기 전용 요약과 합성 규정 Q&A를 제공합니다. 기본 실행은 Mock이며 실제 제공자와 구분합니다.

한 번의 사용을 따라가 보면

  1. 01

    1. 사원 등록에서 조직 변경으로

    관리자는 사원과 로그인 계정을 등록하고 부서·직급을 연결합니다. 이후 소속 변경은 일반 정보 수정 대신 발령 흐름으로 수행해 변경 전후 정보와 작성 시점을 남깁니다. 퇴사는 이력을 지우는 대신 계정 활성 상태를 바꿉니다.

  2. 02

    2. 신청·승인·취소와 휴가 잔액

    사원은 잔액을 확인하고 연차·반차 등을 신청합니다. 대기 중 신청은 예약량, 승인된 신청은 사용량으로 반영합니다. 관리자는 본인 신청을 결재할 수 없으며, 이미 처리된 신청이나 시작일을 지난 취소 등은 서버 규칙으로 막습니다.

  3. 03

    3. 월별 데모 급여 생성·확정

    관리자는 급여 설정을 바탕으로 월별 초안을 만들고 전체 결과를 확인한 뒤 확정합니다. 초안 재계산과 확정 상태를 구분하며, 사원에게는 본인의 확정 명세만 공개합니다. 명세의 고정 비율 공제는 화면과 문서에서 데모로 안내합니다.

  4. 04

    4. 확정 평가와 AI 보조

    자기·관리자 평가를 진행한 뒤 확정된 원문·점수·등급을 먼저 보여 줍니다. AI 요약은 별도 읽기 영역으로 표시합니다. 자연어 검색도 제안과 현재 조건의 비교를 보여 준 뒤 사용자가 적용해야 기존 목록 API를 호출합니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    권한을 통과한 업무 API

    브라우저는 React 화면에서 Spring Boot API를 호출하고, 서버가 JWT와 계정 활성 상태·역할을 확인합니다. 사원 정보, 발령, 근태·휴가, 급여·평가의 조회 범위를 업무별로 나누며 퇴사 시 계정을 비활성화합니다. 화면의 버튼 숨김과 별개로 API에서도 접근을 판단합니다.

  2. 02

    상태·감사·알림의 같은 커밋

    발령은 사원 행을 잠근 뒤 이전 값을 읽어 현재 소속·이력·감사를 함께 갱신합니다. 휴가 처리도 업무 변경·감사·알림을 한 트랜잭션으로 묶습니다. Flyway V1~V4로 스키마를 확장하고, 확정 급여에는 당시 이름·소속·금액·공제율과 산식을 스냅샷으로 보존합니다.

  3. 03

    제품 AI와 개발 AI의 분리

    서버의 LlmClient 뒤에 Mock·Anthropic·Ollama 경로를 둡니다. 호출 전에 권한·입력·호출 상한을 검사하고 결과의 JSON 구조·허용값·인용을 검증합니다. 검색에는 카탈로그, 요약에는 허용된 코멘트, 규정 Q&A에는 고정 합성 문서만 제공합니다. 개발에 사용한 Claude Code·Codex의 협업은 이 제품 호출 경로와 별개입니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

휴가 중복 신청과 잔액 경합을 함께 다루기

마주한 문제
동시에 두 신청이 같은 잔액을 보고 승인되면 허용 일수를 넘길 수 있습니다. 승인·취소·퇴사 처리가 서로 다른 잠금 순서를 사용해도 경합 문제가 생깁니다.
선택과 구현
사원 → 잔액 순서로 잠그고, 대기·승인 신청의 합계에서 reserved·used를 다시 계산합니다. 날짜 중복은 오전·오후 반차의 비트 마스크로 검사하며 상태 변경·감사·알림을 같은 트랜잭션에서 처리합니다.
남은 비용과 한계
처리 순서가 명확해지는 대신 동일 사원의 요청은 직렬화됩니다. 평일 중심 휴가 계산 등 정책은 단순화되어 있어 실제 회사 규정 전체를 대신하지 않습니다.
LeaveService — 잠금·잔액 재계산·상태 전이 ↗
CASE 02

월 단위 원자성과 확정 스냅샷

마주한 문제
급여 생성 중 설정이 누락되거나 두 관리자가 같은 월을 확정하면 일부 명세만 남거나 확정 내용이 달라질 수 있습니다. 현재 사원 정보를 매번 조인하면 과거 명세도 바뀝니다.
선택과 구현
월별 MySQL GET_LOCK과 행 잠금을 함께 사용하고 동일 JDBC 연결에서 커밋·롤백 뒤 named lock을 해제합니다. 설정 누락·감사 실패는 월 전체를 롤백하며, 확정 뒤 수정·재생성을 막고 이름·소속·금액·산식·처리자를 스냅샷합니다.
남은 비용과 한계
동일 월 작업이 겹치면 즉시 PAYROLL_BUSY로 돌려보냅니다. 월 전체의 일관성을 우선하는 설계이며 일할 계산과 실제 세법·4대보험 산정은 포함하지 않습니다.
ADR 0110 — 월 잠금과 확정 스냅샷 ↗
CASE 03

AI 제안의 적용 시점과 화면 수명 제한

마주한 문제
늦게 도착한 응답이 다른 계정이나 새 요청 화면에 섞일 수 있고, 검색 제안·평가 요약이 기존 업무 데이터를 자동 변경하면 사용자의 의도와 어긋납니다.
선택과 구현
사용자의 명시 실행만 생성 요청으로 연결합니다. 검색 제안은 다섯 필드의 적용 전후 비교와 확인을 거쳐 전체 교체하고, 평가 요약에는 저장·제출 경로를 두지 않습니다. 입력·응답은 컴포넌트 메모리만 사용하며 화면 해제·계정 변경 시 요청을 중단하고 이전 응답을 버립니다.
남은 비용과 한계
자동 적용·공유 캐시·자동 재시도의 편의보다 사용자의 확인과 정보 수명을 우선했습니다. 브라우저 요청 중단이 제공자 처리나 비용 취소를 보장하지는 않습니다.
ADR 0206 — 명시 실행과 일시적 결과 ↗
05 / ROLE & CONTRIBUTION

맡은 역할과 기여

사원·조직·휴가·급여·평가를 하나의 업무 흐름으로 연결하도록 요구사항과 완료 기준을 정했습니다. 사원의 소속이 바뀔 때 이력을 남기는 일, 휴가 신청과 잔액을 함께 관리하는 일, 급여·평가 확정 뒤 당시 결과를 보존하는 일을 주요 시나리오로 삼아 개발 방향을 잡았습니다.

Claude Code에는 설계 검토·UI 시안·이미지 검수를, Codex에는 백엔드·프런트 구현·테스트·문서와 통합 검수를 맡겼습니다. API 계약과 ADR로 병행 작업의 기준을 맞추고, 화면 피드백을 수정·재촬영으로 이어가며 결과를 확인했습니다. 요구사항을 구체화하고 AI 도구의 작업을 조율하는 역할에 집중했습니다.

현재 범위와 남은 과제

  • 제품 AI는 Mock으로 시연했습니다. Anthropic·Ollama 설정과 어댑터는 있지만 실제 추론·응답 품질·비용 평가는 남아 있습니다.
  • 급여는 고정 비율 데모이며 근태·연차 정책도 단순화했습니다. 실제 인사·급여 운영에 적용하려면 업무 규칙과 계산·보안 검증이 필요합니다.
  • sessionStorage 토큰의 XSS 노출 가능성이 있습니다. 로그인 속도 제한·개별 JWT 폐기·전체 CSP 적용은 보완 과제입니다.
  • 운영 배포·부하·침투 테스트와 포괄적인 접근성 검증은 남아 있습니다. 일부 디자인 피드백과 빌드 청크 경고도 후속 수정 항목입니다.

다음에 보완할 것

  • 실제 제공자를 별도 평가 환경에서 연결해 허용 데이터 전송·오류 처리와 인용 의미 정확성을 검증하고 Mock 결과와 분리해 기록합니다.
  • 인증 저장 방식·로그인 제한·토큰 폐기 정책을 보완한 뒤 운영 환경의 보안·접근성·동시성 검증 범위를 넓힙니다.
