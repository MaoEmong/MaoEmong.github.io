01 / CONTEXT

어떤 문제에서 시작했나요?

여행 서비스에서는 계획을 만드는 화면, 숙소를 찾는 지도, 예약 내역과 캘린더가 서로 다른 작업처럼 나뉘기 쉽습니다. 여기 한국은 날짜별 계획과 장소 탐색, 숙소 예약, 여행 후 기록을 한 서비스 안에서 연결하는 것을 목표로 했습니다. 프로젝트 방향과 문서를 함께 관리하면서 도메인별 기능이 같은 사용자 흐름을 따르도록 정리했습니다.

담당한 마이페이지와 챗봇은 여러 기능을 다시 모으는 접점입니다. 마이페이지는 사용자·예약·계획 정보를 화면이 원하는 형태로 조합해야 하고, 챗봇은 일반 대화와 실제 예약 조회를 구분해야 합니다. 자연어 답변이 그럴듯하더라도 조회 자료가 없으면 확정적인 예약 안내를 내보내지 않는 것이 중요한 기준이었습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

계획과 지도 탐색

여행 계획과 날짜별 일정, 지도 기반 관광지·숙소 탐색을 제공합니다.

02

예약과 내 정보

숙소 예약·상세·완료 흐름과 마이페이지를 구성했습니다.

03

커뮤니티와 챗봇

게시판과 회원 기능, 챗봇 등 여행 전후의 기능을 함께 다룹니다.

한 번의 사용을 따라가 보면

  1. 01

    계획을 만들고 장소 정리

    로그인한 사용자가 여행을 생성하고 날짜별 장소를 추가합니다. 지도와 날씨를 참고해 여행의 동선을 정리합니다. 이 기능들은 팀 전체의 결과이며 본인 담당 기능의 앞단 흐름입니다.

  2. 02

    숙소를 선택하고 예약

    지역·숙소 탐색에서 체크인 정보와 예약 확인, 완료 화면으로 이어집니다. 예약 정보는 여행 계획과 연결되어 이후 마이페이지와 챗봇에서 다시 조회할 수 있습니다.

  3. 03

    내 여행과 예약을 한곳에서 확인

    마이페이지에 다가오는 여행과 예약 요약을 보여주고 목록·상세로 연결합니다. 예약 상태별 목록과 빈 상태, 비밀번호 변경 결과에 맞는 화면 정보를 서비스 계층에서 구성합니다.

  4. 04

    대화로 실제 정보를 조회

    사용자가 내 여행이나 예약을 질문하면 챗봇이 해석한 도메인의 조회를 수행합니다. 충분한 자료가 있을 때 답변을 생성하고, 자료가 없거나 날씨의 지역·날짜가 빠진 경우 구체적인 질문을 요청합니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    도메인별 서버 렌더링

    Controller·Service·Repository 책임을 나누고 trip, booking, calendar, board, mypage, chatbot 등 도메인 패키지를 유지합니다. Mustache의 pages와 partials로 화면과 공통 조각을 구성하며 필요한 동작은 페이지별 JavaScript로 연결합니다.

  2. 02

    마이페이지용 조회 모델

    MypageService가 사용자 확인, 다가오는 예약·여행의 제한된 조회, 화면 DTO 생성을 조합합니다. 예약 상세는 BookingService를 재사용하고, 비밀번호 변경은 별도 검증 뒤 PasswordEncoder로 저장합니다.

  3. 03

    해석·조회·답변의 분리

    ChatbotService는 LLM의 해석을 일반 대화 또는 DB_QA로 나눕니다. 정해진 도메인·의도·기간·키워드로 QueryPlan을 만들고 ChatQueryRepository나 WeatherService를 호출한 뒤 QueryBlock을 답변 자료로 전달합니다.

  4. 04

    사용자 맥락을 가진 조회

    예약·여행·캘린더 조회는 로그인 사용자의 ID를 조건에 포함합니다. 모델이 만든 SQL을 직접 실행하는 방식 대신 서버에 정의된 JPQL과 파라미터를 사용하며, 조회 개수와 한 번에 처리할 계획 수를 제한합니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

여러 도메인을 마이페이지 DTO로 조합

마주한 문제
프로필·예약·여행 계획과 수정 결과를 템플릿에서 직접 조합하면 화면 조건과 업무 로직이 뒤섞입니다.
선택과 구현
서비스에서 요약 조회와 상태별 MainPageDTO를 만들고, 예약 상세 처리는 BookingService를 재사용했습니다. 다가오는 예약과 계획은 각각 최대 2개로 제한합니다.
남은 비용과 한계
화면 전용 DTO와 조회 모델을 관리해야 하고 날짜 기준이 바뀌면 관련 테스트도 조정해야 합니다. 대신 템플릿에 업무 조건이 퍼지는 범위를 줄입니다.
MypageService 구현 ↗
CASE 02

LLM 해석을 허용된 조회로 연결

마주한 문제
자연어 질문을 곧바로 SQL로 실행하면 도메인 범위와 사용자 데이터 조건을 통제하기 어렵습니다.
선택과 구현
BOOKING·TRIP·CALENDAR·BOARD·WEATHER 도메인과 QueryPlan을 사용하고, 서버의 정해진 조회로 변환합니다. 개인 데이터 조회에는 userId를 조건으로 넣고 바인딩 파라미터와 결과 수 제한을 사용합니다.
남은 비용과 한계
질문할 수 있는 범위는 구현한 도메인과 의도로 제한됩니다. 지원하지 않는 자유로운 분석까지 처리하는 범용 SQL 에이전트로 설명하지 않습니다.
ChatQueryRepository 구현 ↗
CASE 03

정보가 부족하면 답변 생성을 멈춤

마주한 문제
조회가 비었거나 후속 질문의 날짜·지역이 빠졌는데도 답변을 생성하면 사용자가 실제 정보로 오해할 수 있습니다.
선택과 구현
대화에서 해석된 맥락으로 누락된 슬롯을 보완하고, QueryBlock 전체의 자료 존재 여부를 확인합니다. 부족하면 hasSufficientData=false와 안내문을 반환하며 날씨 질문에는 지역·날짜 예시를 제공합니다.
남은 비용과 한계
일부 도메인 결과만 비어도 전체 답변을 보류하므로 답변 가능한 정보까지 덜 제공할 수 있습니다. 부분 응답 정책은 별도 개선 대상입니다.

05 / ROLE & CONTRIBUTION

본인의 역할과 기여

README에 기록된 본인 역할은 프로젝트 방향, 문서 체계, 리팩토링, 마이페이지, 챗봇입니다. 기능 목록뿐 아니라 패키지와 계층 책임, 템플릿 재사용, 기능별 테스트 기준을 공통 문서로 정리한 맥락에서 담당 결과를 설명합니다.

구체적인 구현 사례는 마이페이지의 조회·화면 상태 조합, 비밀번호 검증, 챗봇의 해석·도구 조회·자료 부족 응답입니다. 지도·날씨·사용자 인증·여행 계획·커뮤니티 전체를 본인 단독 구현으로 묶지 않고 팀의 기능 연결 경험으로 소개합니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

아래 결과는 연결된 공개 문서의 기록입니다. 이 소개 페이지를 갱신하면서 원본 프로젝트의 검사를 다시 실행한 결과는 아닙니다.

마이페이지 서비스 검사

프로필과 예약·여행 요약, 빈 목록, 취소 예약 제외, 상세 조회, 비밀번호 동일값 거절과 인코딩 저장을 다루는 테스트가 있습니다.

SpringBootTest의 공개 코드 기준입니다. 날짜가 고정된 시드·기대값이 있어 현재 시점의 통과 여부는 재실행이 필요합니다.

챗봇 분기 검사

날씨 도구, 후속 맥락 보완, 필수 조건 누락, 일반 대화, 빈 조회와 자료가 있는 조회의 테스트가 공개되어 있습니다.

LLM·날씨·조회 저장소를 모킹하는 서비스 분기 검사입니다. 실제 모델 답변의 정확도를 측정한 결과는 아닙니다.

현재 소개 범위와 한계

  • 공개 실행 안내는 localhost 기준이며 현재 운영 배포 상태를 확인한 프로젝트는 아닙니다.
  • 챗봇의 모킹 테스트는 실제 OpenAI 응답 품질·외부 API 장애·대화 비용까지 검증하지 않습니다.
  • 마이페이지의 날짜 의존 테스트는 시간이 지나면 시드와 기대 조건을 함께 검토해야 합니다.
