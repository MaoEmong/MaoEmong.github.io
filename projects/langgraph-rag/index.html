01 / CONTEXT

어떤 문제에서 시작했나요?

개인 문서를 검색해 답하는 시스템에서는 질문과 표현이 다른 문서를 찾는 능력, 정확한 단어를 놓치지 않는 능력, 답변에 필요한 문맥을 함께 모으는 능력이 필요합니다. 한 번의 벡터 검색과 생성만으로는 어떤 단계에서 근거가 부족해졌는지 드러나지 않습니다. 이 프로젝트는 검색·답변을 단계별 상태와 판단으로 나누는 데 초점을 두었습니다.

검색 전략을 더하면 품질뿐 아니라 지연과 운영 복잡도도 늘어납니다. 하이브리드 검색, 부모 청크 확장, 선택적 리랭커, 제한된 재질의를 각각 조절하고 평가할 수 있도록 구성했습니다. 응답 성공 여부와 키워드·인용 확인, 그래프 처리 시간을 나누어 읽는 도구도 함께 마련했습니다.

02 / PRODUCT FLOW

사용자에게 이어지는 흐름

01

문서와 대화

파일 인제스트·질의응답·대화 스레드 조회와 초기화를 제공합니다.

02

검색과 재질의

Chroma·FTS5 하이브리드 검색, 부모 청크 확장과 제한된 재검색을 구성합니다.

03

평가 실행 도구

배치별 실행과 로그 저장, 실패 요약, 성공·키워드·인용·지연 통계 분석 도구를 제공합니다.

한 번의 사용을 따라가 보면

  1. 01

    문서 적재

    파일이나 디렉터리를 인제스트하고 문서를 청크·메타데이터·벡터로 저장합니다. OCR은 이미지 자체를 이해하는 멀티모달 검색이 아니라 텍스트 추출을 통한 검색 경로입니다.

  2. 02

    스레드를 지정해 질문

    사용자가 thread_id와 질문을 보내면 그래프가 검색 필요 여부를 판단합니다. 스레드 조회·초기화 API를 통해 개인 대화 흐름을 관리합니다.

  3. 03

    검색 자료로 답변 구성

    필요한 경우 Dense·Sparse 검색과 부모 청크 확장을 수행하고 자료를 생성 단계에 전달합니다. 선택적 리랭커가 꺼진 설정과 켜진 설정을 구분해 실험할 수 있습니다.

  4. 04

    근거가 부족하면 제한적으로 재검색

    문서와 인용 수가 설정 기준에 못 미치면 질문을 검색용 키워드로 다시 쓰고 검색 단계로 돌아갑니다. 시도 횟수 상한에 도달하면 finalize로 진행해 무한 반복을 막습니다.

  5. 05

    평가를 배치로 실행

    동일한 평가 케이스를 여러 배치로 나누어 실행하고 결과와 실패 요약을 저장합니다. 그래프 내부 시간과 클라이언트에서 측정한 시간을 별도로 집계하도록 구성했습니다.

03 / ARCHITECTURE

구조와 책임을 나눈 방식

  1. 01

    실제 StateGraph의 조건 분기

    graph.py가 route·retrieve·db_plan·db_query·generate·requery·finalize를 LangGraph 노드로 등록합니다. 검색 필요 여부와 재질의 필요 여부로 분기하며 각 노드와 전체 실행 시간을 응답의 timing에 반영합니다. DB 노드가 그래프에 있다는 사실과 실제 DB 실연동 검증은 구분합니다.

  2. 02

    문서·벡터·대화의 저장 분리

    문서 정보와 대화 체크포인트는 SQLite, 벡터는 영속 Chroma에 둡니다. 인제스트는 source_path와 content_hash로 동일 파일을 건너뛰고 변경 파일을 교체하는 정책을 README에 명시합니다. 이미지 입력은 OCR로 추출한 텍스트를 검색 대상으로 사용합니다.

  3. 03

    하이브리드 검색과 문맥 확장

    Dense 검색과 SQLite FTS5 검색을 각각 수행해 chunk_id로 합치고 순위의 역수를 더해 정렬합니다. parent_id가 같은 청크를 확장해 문맥을 보충하며 리랭커는 off·auto·always 설정으로 선택합니다.

  4. 04

    평가를 위한 별도 실행 도구

    배치 러너가 서버 기동·health 확인·평가·종료를 반복하고 결과를 병합합니다. 분석기는 성공률·키워드·인용·지연 임계값과 장시간 검사 드리프트를 확인하고, 경고 시 실패 코드로 종료할 수 있습니다.

04 / ENGINEERING CASES

구현하면서 선택한 것

기능 목록 뒤에 있는 문제와 선택, 그 선택이 남긴 비용을 정리했습니다.

CASE 01

서로 다른 검색 점수는 순위로 결합

마주한 문제
임베딩 거리와 FTS5 점수는 같은 척도가 아니므로 원점수를 그대로 더하기 어렵습니다.
선택과 구현
각 검색 결과의 순위를 역수 점수로 바꾸고 chunk_id로 병합합니다. 검색 뒤 parent_id 기반 문맥 확장과 선택적 재정렬을 수행합니다.
남은 비용과 한계
순위 결합은 단순하고 추적하기 쉽지만 검색별 점수 차이의 크기를 버립니다. 부모 확장도 문맥을 늘리는 만큼 불필요한 자료와 토큰이 늘어날 수 있습니다.
retrieve 노드 ↗
CASE 02

재질의 판단을 별도 노드로 분리

마주한 문제
근거가 없는 검색을 계속 반복하거나 모든 질문에 재검색을 적용하면 지연과 API 사용량이 커집니다.
선택과 구현
검색 필요 여부, 문서·인용 최소 수와 attempt 상한을 확인합니다. 조건을 만족할 때만 질문을 다시 쓰고 retrieve로 돌아가며, 재작성 실패 시 원문을 유지합니다.
남은 비용과 한계
문서·인용 수는 근거의 의미적 정확성을 보장하지 않습니다. 재질의 상한은 지연을 통제하지만 어려운 질문을 충분히 탐색하지 못할 수 있습니다.
requery 노드 ↗
CASE 03

평가 실행의 실패를 산출물로 남김

마주한 문제
긴 평가 도중 서버가 불안정해지면 검색 품질 문제와 실행 환경 문제를 구분하기 어렵습니다.
선택과 구현
배치마다 서버를 재기동하고 health 확인 후 평가합니다. 배치별 로그·실패 단계·오류를 저장하고 성공·키워드·인용·지연 통계를 병합합니다.
남은 비용과 한계
배치마다 서버를 재시작하므로 연속 운영 중의 안정성은 별도로 검사해야 합니다. 평가를 재현하려면 입력·결과 산출물과 모델·설정·실행 환경을 함께 보관해야 합니다.

05 / ROLE & CONTRIBUTION

맡은 역할과 기여

FastAPI 인터페이스와 문서 인제스트·저장, LangGraph 기반 질의응답 흐름을 구성했습니다. 검색 필요 여부와 근거 부족 시 재질의 판단을 별도 노드로 나누고, 하이브리드 검색·부모 청크 확장·선택적 리랭커를 조합할 수 있도록 연결했습니다.

검색 설정과 재질의 상한을 조절하고 노드별 처리 시간을 기록하도록 구성했습니다. 배치 평가 실행, 실패 단계와 오류 로그 저장, 성공·키워드·인용·지연 통계 분석 도구도 함께 마련해 검색 방식의 차이와 실행 중 실패를 살펴볼 수 있도록 했습니다.

06 / EVIDENCE & LIMITS

무엇을 확인했고, 무엇이 남았나요?

프로젝트 검증 당시의 실행 기록과 코드에 구성한 테스트 항목을 정리했습니다. 각 항목에 실행 조건과 추가 확인이 필요한 범위를 함께 적었습니다.

검색·재질의 그래프 구성

StateGraph에 노드와 route 분기를 등록하고, 재검색 루프와 노드별 timing 측정을 구현했습니다.

그래프 구조와 조건은 연결된 코드에서 확인할 수 있습니다. 외부 모델을 연결한 전체 질의의 재실행은 남아 있습니다.

평가 자동화 도구

분석기가 성공·키워드·인용·p90 지연의 임계값을 검사하고, fail-on-alert 옵션에서는 기준 미달 시 종료 코드 2를 반환하도록 구성했습니다.

평가 기준을 자동 검사하는 도구의 구현 범위입니다. 현재 설정의 임계값 충족 여부와 답변의 사실 정확도는 결과를 다시 수집해 평가해야 합니다.

이전 평가 기록과 재현 과제

이전 README에 50케이스의 성공·키워드·인용 통과와 graph p90 약 6.7초를 기록했습니다.

당시 결과·분석 JSON은 공개 저장소에 포함되어 있지 않습니다. 실행 환경과 원자료를 함께 정리하고 재실행해 최신 결과를 남기는 일이 과제입니다.

검증 근거 보기 ↗

현재 범위와 남은 과제

  • 이전 50케이스 평가의 원본 결과·분석 JSON은 공개 저장소에 포함하지 않았습니다. 모델·설정·입력과 함께 재실행 결과를 정리해야 합니다.
  • DB QuerySpec·MySQL 어댑터는 준비 단계입니다. 실제 DB 연결 후 스모크 검증이 필요합니다.
  • 리랭커·OCR은 선택 기능으로 모델·GPU·Tesseract 등의 실행 환경에 영향을 받습니다.
  • 키워드·인용 개수 외에도 답변의 사실성, 문서에 포함된 악의적 지시에 대한 방어 능력을 평가해야 합니다.

다음에 보완할 것

  • 비밀정보를 제외한 평가 입력·결과·분석 JSON과 모델·설정·커밋을 함께 공개해 재현 가능하게 만들기
  • 검색 실패·근거 불충분·재질의 상한 시나리오를 별도로 비교하고 DB 준비 기능의 실제 연결 결과를 분리 기록하기
